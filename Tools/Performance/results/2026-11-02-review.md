# PR #190 review follow-up — 2026-11-02

Production revision: **`ebc076a`**. This follow-up evaluates the ten reported concerns as summarized by the reviewer, who had not reproduced them. It records targeted regression checks after fixes; the [reference acceptance](2026-11-02-acceptance.md) remains the source for the larger percentile and retention series.

## Findings and disposition

| Concern | Evidence and action |
| --- | --- |
| PDF section index advances before successful rendering | Confirmed failure-safety defect. The existing caught exception types already failed the job, but other exceptions could escape to the watcher and leave the job queued with a skipped section. Sessions now advance only after success and permanently reject further rendering/publication after a section failure. Background jobs terminate on any section/rendering exception, discard the old download, and cannot restart on another advance. |
| Media discovery misses `AutolinkInline` | Reproduced for standalone YouTube and Vimeo angle-bracket autolinks. Discovery now considers these nodes before falling back to the existing rendered-HTML decision. Inline autolinks within a sentence still do not become standalone embeds. |
| Initial PDF failure no longer exits `serve` | Confirmed, intentional behavior change under the approved preview/download readiness design. Documented explicitly in [`mdu serve`](../../../Docs/Usage/serve.md), including the exit-code difference and strict `render`/`pdf` alternatives. Integration coverage now starts with both valid and invalid PDF input and verifies recovery. |
| Asset requests wait for the rendering lock | Reproduced with the lock deliberately held: CSS timed out. Non-HTML requests unrelated to pending page/alias output now bypass the lock; pending PDFs immediately return their unavailable status. The pending-output lookup is concurrent. HTML reads remain serialized with writers, including PDF sections; this does not make a single PDF section preemptible. |
| Process-lifetime Markdown snapshots | The cache belongs to each `MarkdownFile` node. Retaining that same node across a source write does return its old snapshot until `InvalidateMarkdown` is called; this requirement is explicit in the method documentation. The current non-serve mutators do not reread written files through those old nodes: `fix` builds its graph after migrations and subsequently rewrites links with direct file reads; `page move` and `page links` use direct file reads without `MarkdownFile` nodes. Same-process regression tests verify these paths; see the follow-up below. Serving invalidates observed changes before reusing its nodes. |
| Repeated Git metadata work | Signature validation still performs metadata I/O on unchanged-history edits; this is the correctness cost of detecting history/configuration changes without trusting body edits. There is no new evidence here of a budget failure. Existing commit/worktree/packed-ref/shallow-history tests and reference Git measurements remain applicable; no speculative metadata cache was added. |
| Duplicated ancestor walk | A cache miss can discover the repository for the signature and again for the original Git query. A cache hit avoids the Git query. This is finite duplicate work, not a demonstrated correctness defect; retained pending future profiling evidence. |
| Delegate-keyed lexer cache allocation | Not reproduced in Release on .NET 10. After warm-up, **200,000** `Lexer.ForLanguage` calls cycling language names, aliases and two unknown names allocated **0 bytes** on the calling thread. Cache keys remain the finite grammar factories, rather than arbitrary input strings. |
| Generated-regex fields plus methods | Extra field aliases are a style choice around generated singleton regex accessors; no duplicate regex compilation or incorrect behavior was demonstrated. Existing parser/renderer tests pass; no unrelated formatting rewrite. |
| Process-wide diagram limits | Introduced by [PR #189](https://github.com/capjan/mdu/pull/189), merge commit `2ca86130be88294de36b1a838aad382305b9a3ee`, which is the GitHub-reported base of PR #190. `DiagramRenderer.cs` has identical Git blob IDs at that base and the PR head: `36bf0a715f2be61a0d9d4fe7aad3bb6478a761ae`. This PR does not introduce the limits. Multiple independently configured sites within one process remain a pre-existing limitation; ordinary CLI previews run in separate processes. |

## Non-serve snapshot verification and diagram provenance

The second review correctly asks for non-serve call-path evidence rather than relying on serve invalidation alone. The suspected write-then-read pattern was checked in `FixCommand.Execute`, `PageCommand.Move`/`Links` and `PageMover.Plan`/`Apply`:

- `fix` completes its MkDocs migrations before creating the metadata/lint graph. Later link rewrites call `File.ReadAllText`, move/write the files and return; there is no subsequent read through the earlier graph nodes.
- `page move` plans link rewrites using `File.ReadAllText`, then applies the moves and writes. Another move or `page links` in the same process reads the current files again. These paths do not use `MarkdownFile.ReadMarkdown`.
- `FixAndSubsequentGraphsReadRewrittenFilesWithinTheSameProcess` primes a graph snapshot, runs `fix` using the same `GraphBuilder`, and verifies fresh graph nodes contain rewritten links. It also verifies the retained old node stays stale until explicitly invalidated. `RepeatedMovesAndLinkReadsSeeNewContentWithinTheSameProcess` reuses one `PageCommand` for two moves and link queries, including an intervening content edit, and verifies that the latest link is rewritten and found.

The targeted Release run passed **58 tests, with 5 platform skips and zero failures**, including both new cases and the existing fix/page/snapshot cases. This establishes the tested CLI paths; it does not promise automatic freshness for arbitrary consumers retaining old `MarkdownFile` nodes. No source-read behavior was changed in this follow-up.
