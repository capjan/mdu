# End-to-end render and serve baseline — 2026-11-02

Investigation for [#188](https://github.com/capjan/mdu/issues/188). Production revision: **`74ada4a285fdb7cfbb2fc53ff251b7f1ff6e61c1`**, current `main` when fetched. No production optimization was implemented. [Reproduction procedure and measurement definitions](../README.md); [raw observations, environment and nested profiles](2026-11-02.json.gz).

## Findings

- Full fresh-process render medians are **508 ms / 1,069 ms / 4,089 ms** for the 6 / 53 / 503-page workloads. Serve initial HTTP availability is **560 ms / 1,161 ms / 4,193 ms**.
- Single-page edits are incremental in written output, but still run site-wide media discovery and PDF-link preflight. On the 503-page corpus, a body edit takes **400 ms** end to end and allocates about **1,120 MiB** during warm edit processing. Repeated rendering for media discovery is the strongest next target.
- The large render allocates approximately **4.7 GiB**, with only **156 MiB peak process RSS**. Allocation volume is not resident or retained memory. Managed memory after collection settles during repeated body edits; this short experiment does not prove absence of leaks.
- Navigation construction and PDF-link preflight are the next two bounded opportunities. Disk reads, search serialization, and OpenAPI document reparsing are not the dominant measured costs. The evidence does not justify reopening the search extraction design.

| Call count per complete render | small | docs | large |

| Markdown file reads | 30 | 265 | 2,515 |

| OpenAPI expansion calls (including no-op pages) | 12 | 106 | 1,006 |
| Page search extraction | 6 | 53 | 503 |

Ordinary Markdown files are read **five times** per render: metadata, assets, PDF preflight, media discovery and final page processing. These are real `File.ReadAllText` calls for this non-imported corpus. The large render's reads allocate 30.5 MiB and account for about 45 diagnostic ms (roughly 1% of its measured command). A raw-file cache alone is therefore a lower-priority intervention than the downstream repeated work. Parsing has different pipelines and responsibilities; these counts do not justify sharing every AST blindly.

The large corpus renders its 101 PlantUML diagrams **202 times**, for media discovery and actual output, and calls the layered layout 2,424 times. Referenced specs are loaded/read/hashed 202 times, but parsed into OpenAPI documents only **11 times**: the existing parse cache already works. It allocates about 2 MiB for those document parses, far below the subsequent expansion/rendering volume. Search serialization is about 5 diagnostic ms and 6 MiB. Cold icon set loads happen once per used set per process (about 41 ms small and 46 ms large in aggregate); `docs` activates more sets through icon search. They do not recur per warm edit. None of these measurements supports a DOM-only search rewrite.

Three large **body-edit profiles** have median internal work of **324 ms**, before the watcher debounce: site-wide media scan **197 ms**, PDF-link preflight **90 ms**, actual changed-page processing **2.0 ms**, search write **2.1 ms**, plus setup/dependencies/reconciliation. They perform **1,010 Markdown reads and 1,663 parse calls**, despite rewriting one page. The media scan allocates about **966 MiB** in those profiles. A complete initial serve reads each ordinary Markdown file six times because it additionally builds the dependency index; full rebuilds preserve the same general pipeline.

## Correctness and limits

- Every baseline/profile/memory render and server series validates the fixture's content, stable heading anchor, breadcrumb/sidebar and relative links, SVG diagram, code highlighting, API paths, one exact section search entry, consent placeholder and absence of eager iframes/PDF files. Every edited marker reaches HTTP; relevant markers also reach search. SSE selection and HTML rewrite counts are asserted.
- Full-file SHA-256 equality between freshly rendered normal and detailed diagnostic builds passed for **15 / 108 / 1,099 files**, including search, generated specification pages and assets. This confirms instrumentation preserves output for these inputs. Manifest digests are in `compare.json` in the raw artifact.
- `dotnet test Mdu.sln --configuration Release --no-build`: **1,439 passed, 6 platform-conditional skips, 0 failed**. Release solution build: **0 warnings, 0 errors**. No production sources or strict `pdf-hidden` behavior changed.
- The additional browser check could not run: the connection exposed only embedded MCP Apps and no browser capable of navigating the local preview. Consequently interactive consent acceptance/revocation, browser search interaction, keyboard traversal and browser reload/display were **not** verified in this run. Static consent structure and byte identity were verified; do not present these as browser behavior tests.
- This is one machine, one JIT execution mode, synthetic repetition for the large case, warm filesystem caches, and small sample counts. It excludes PDF generation, network/import costs, full Git history and a cross-platform matrix. The detailed profiler measurably perturbs the large workload; stage costs are attribution evidence with bounded precision.

## Ranked next work

1. **Avoid full-site HTML rendering just to rediscover media providers on each edit.** Strongest evidence: every body edit visits all pages; 197 of 324 diagnostic processing ms and roughly 966 MiB go to that path on `large`, while the actual page needs about 2 ms. A follow-up should preserve per-page provider summaries and recompute only affected summaries, with a full refresh when provider membership affects all pages. The upper bound is that measured scan, not a guaranteed 197 ms speedup; some work and initial discovery remain necessary. Expected benefit is lower common edit latency and substantially less GC traffic; the tradeoff is a small retained summary plus invalidation logic. Correctness risks: standalone versus inline/code/HTML links, multiple pages sharing a provider, removals, imports and the site-wide consent dialog. Test them explicitly, including real browser consent/revocation. This change must not weaken PDF validation or change search extraction.
2. **Reuse stable navigation entries within a render visitor.** Strong evidence for repeated construction: `BuildNavigation` reconstructs/orders/resolves the same site entries 503 times, about 680 diagnostic ms and 385 MiB, versus 5 ms at 53 pages. The immutable site-level entries can be investigated separately from per-page current/ancestor flags and relative URLs. Only part of that cost is removable; 770 MiB of emitted navigation strings and the resulting HTML bytes also have real output semantics. Expected benefit is full render/full rebuild latency and allocation reduction on large sites; retained entries trade O(N) memory for less repeated construction. Risks: escaped paths, hidden/top navigation, relative links, current sections, pagination and generated specification pages. Require identical output and a repeated normal-build comparison before claiming a percentage.
3. **Reduce repeated PDF-link preflight on PDF-free warm edits.** Strong path evidence: the unchanged full site is re-expanded/reparsed for a one-page save; about 90 diagnostic ms and 108 MiB in the large body-edit profile, versus roughly 317 ms in a fresh full render. Investigate retaining dependency-aware link summaries or reusing results already computed for unchanged pages. Benefit is another bounded portion of edit latency and allocations; summaries cost retained memory and harder invalidation. Risks are more serious: first/last PDF link, selected roots, external spec edits, imports, malformed links and the strict `pdf-hidden` contract. Keep existing validation authoritative; do not add a substring shortcut that bypasses it. Priority follows media discovery and navigation because its measured removable share is smaller and correctness risk is higher.

These are follow-up issue/PR proposals, not optimizations included here. No permanent cache, incremental architecture, parallel rendering or new production package was added. HTML assembly/output remains the largest broad full-render bucket, but its residual needs narrower profiling before proposing an additional internal rewrite. OpenAPI document parsing, raw reads, cold icon loading and syntax highlighting are not the highest demonstrated user-impact targets in these measured paths.

## Proposed regression checks and budgets

Use this fixed corpus, the same machine/runtime/mode, and repeated normal runs. These are **provisional local investigation budgets**, not enforced CI thresholds and not portable SLAs. Compare medians; repeat a suspected failure before acting. Alert on >15% regression, and treat >25% with at least 20 ms absolute increase in two repeated batches as actionable. Preserve first-edit observations separately from steady-state saves.
