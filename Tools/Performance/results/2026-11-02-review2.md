# Second PR review follow-up — 2026-11-02

Reviewer baseline: **`b2f6a0c`**. Fixes: **`5ec13fa`**, with the conditional save-settling refinement at **`c9f286b`**. The earlier non-serve snapshot checks did not exercise an aborted serve batch; this review identified a separate, confirmed invalidation defect.

## Disposition of the ten concerns

| # | Concern | Evidence and result |
| --- | --- | --- |
| 1 | Later changed pages retain old snapshots after an earlier failure | Reproduced. Every affected snapshot and prepared expansion is now invalidated before parsing, including before shared rebuild decisions. Unfinished pages are unavailable rather than served as current. After a failed batch, the next save rebuilds fresh sources, metadata and dependencies, covering pages the failed batch never reached. The recovery marker and unfinished-page set are bounded by the current graph; old file-event records are not accumulated. |
| 2 | Pending pages disappear before successful rendering | Reproduced for requests and background work. A page leaves the queue only after successful rendering. Failed pages remain pending, background work skips them, and requests retry them. Repeated failure returns HTTP 500 instead of stale HTML/404; readiness stays incomplete. Recovery refreshes search and aliases before reporting completion. |
| 3 | Exceptions outside the filters are unobserved or stop background work | Reproduced with an injected `NullReferenceException`. Request rendering now logs failures and returns HTTP 500. Background page failures are logged and isolated; the failed page is retriable while other work/server requests continue. Cancellation of the worker wait remains handled by the command's normal shutdown path. |
| 4 | A successfully refreshed OpenAPI sibling is later overwritten by its old pending expansion | Reproduced with a specification-name collision. Changed prepared expansions are discarded; successfully refreshed siblings leave the old queue. Sibling failures propagate to batch recovery instead of being logged and otherwise forgotten. The shifted specification name survives completion of the remaining queue. |
| 5 | A failed shared rebuild destroys the previous pending queue | Reproduced with invalid `mdu.yml`. Old pending work is retained until the replacement graph, search preparation and PDF planning succeed. A valid pending page remains available on demand after configuration parsing fails. This stages the queue replacement, not a transaction over every process-wide renderer setting. |
| 6 | A multi-step save is mistaken for page deletion | Reproduced with a real filesystem watcher and a **50 ms** rename/recreate gap: the old implementation published `reloadAll`. A deletion/rename leaving a known page missing gets another 75 ms after the normal 20 ms batch window. The test now observes a scoped update and unchanged unrelated HTML. Already-completed atomic replacements and ordinary edits have no added settling delay. Arbitrarily long missing-file intervals are not guaranteed to coalesce. |
| 7 | One PDF failure makes all generated PDFs unavailable | **Unchanged availability limitation.** Readiness remains global; pending/failed generation conservatively returns 503 for all generated PDF paths, including unchanged ones. Per-path readiness would improve availability. This is documented explicitly in the processing pipeline; this follow-up does not claim to implement it. |
| 8 | Final PDF assembly/write holds the rendering lock | **Unchanged scheduling limitation.** Layout completion, front matter and final writing are still indivisible. Ordinary no-PDF editing budgets do not cover arbitrary large PDFs. HTML, pending-download status and latest-content checks were repeated separately, without claiming finalization is preemptible. |
| 9 | Generated-regex field/method boilerplate | Cleanup, without a demonstrated correctness failure. No unrelated declaration rewrite; the generated regex behavior remains covered by the existing parser/renderer tests. |
| 10 | Duplicated repository discovery | Cleanup, without a demonstrated failure. No new discovery abstraction or invalidation behavior was added in this correctness follow-up. |

## Failure reproduction and tests

- A controlled two-page change batch failing on invalid import metadata, followed by another save while the error remains, then repair. Both later body text and changed PDF visibility reach the recovered HTML/search/PDF; obsolete text does not. Affected unfinished HTML returns an error until recovery.
- Expected I/O and unexpected null-reference failures, each through HTTP and background pending-page rendering. They verify errors on repeated requests, retained pending/readiness state, and successful retry without restarting.

### Non-blocking transport/logging follow-up

A real TCP client resetting a connection during a 64 MiB sparse-file response reproduced the noisy failure path and an attempted second response after headers were already sent. Known transport failures (`HttpListenerException`, `SocketException`, and an `IOException` wrapping either) now end delivery quietly. Other I/O errors and unexpected renderer errors remain logged; plain `IOException` is deliberately not suppressed. If writing an error response fails after headers were sent, that secondary failure is contained too.

Three regression cases cover the reset and logged I/O/null-reference render failures in `PreviewServerLoggingTest.cs`. After this change, a fresh **full local Release solution run passed 1,510 tests, with 6 platform skips and zero failures**.
